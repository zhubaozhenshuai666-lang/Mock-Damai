# 预约与抢票提交分离

预约计划定义为开售前的版本化填单方案，不是库存预留、价格承诺或订单。用户必须在场次开售前完成预约；开售前修改任意场次、票档、数量或观演人都会使当前版本失效并要求重新完成预约。完成预约只冻结方案和观演人快照，不创建请求、不扣库存；开售后用户手动提交抢票，系统才创建异步抢票请求并进入库存和订单链路。

同一用户同一场次只保留一份有效预约。预约不保证库存或价格，抢票提交时必须重新校验实时演出关系、开售窗口、票档状态和库存。正式订单生成后，订单负责支付、取消和超时关闭，预约计划不再镜像订单状态。请求与预约绑定异常时进入对账态，禁止直接标记失败后重试，以避免重复订单和库存占用。

## Considered Options

- 让完成预约直接创建订单或预扣库存：会把用户的提前配置误当成交易承诺，并扩大库存长期占用。
- 让预约计划持续镜像订单的支付和取消状态：会产生第二套订单状态机和同步失败问题。
- 保留一个同时完成预约和抢票的提交接口：无法表达“未完成预约按普通流程处理”，也无法在开售边界安全锁定方案。

## Consequences

- 场次必须拥有独立的开售时间窗口，不能复用演出开始时间。
- 预约编辑、完成预约和抢票提交必须使用版本条件，开售边界由数据库条件更新裁决。
- 需要为请求绑定失败、消息重复和补偿未完成建立对账与恢复流程。
