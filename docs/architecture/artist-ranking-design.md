# 艺人/乐队排行榜设计与大麦公开机制对比

本文只把大麦公开说明作为事实来源，不把大麦未公开的内部公式当成已知事实。大麦的精确权重、反作弊模型、用户分层、内容审核规则和排序服务实现均未公开。

## 1. 先给结论

当前代码已经实现的是“按内容、兴趣、购票意向、支付、任务五类信号拆分的 Redis ZSET 热度榜”：

- 详情页点击：记录一次艺人兴趣信号。
- 搜索命中艺人：记录一次搜索意图信号。
- 预约计划成功提交创单：记录一次购票意向信号。
- 支付成功：记录一次强转化信号。
- 同一个用户（未登录时为 IP）对同一艺人的同一动作每天去重。
- 同时维护全量、日、周、月四个榜单。
- 额外维护小时桶，并提供最近 24 小时热榜；热榜使用可配置的指数衰减，默认半衰期为 6 小时，减少长期累计分数对即时热度的遮蔽。
- 认证用户和匿名用户使用不同质量系数，匿名请求默认只贡献 35%。
- 同一艺人高基数事件使用对数边际增量，避免分数无限线性增长。
- Redis 故障时榜单写入/读取降级，不阻断详情、搜索、下单和支付主链路。

这不是“大麦算法复刻”。大麦公开描述的“最热现场”是“真实演出现场综合互动热度”，是多维度内容互动指标，并且公开提到任务贡献、内容热度和约 10 分钟更新一次；公开资料没有给出精确公式。参见[大麦相关公开说明](https://www.sina.cn/news/detail/5311212838719304.html)。

## 2. 大麦公开信息能确认什么

根据大麦公开说明，可以确认以下行为，而不能确认内部实现细节：

| 维度 | 公开可确认的信息 | 不能据此推导的内容 |
|---|---|---|
| 榜单对象 | 用户可以从艺人页或演出详情进入“最热现场”相关入口 | 榜单内部成员究竟是艺人、演出项目、内容作品还是多级实体 |
| 指标含义 | “真实演出现场综合互动热度” | 点击、搜索、评论、分享各自的准确权重 |
| 信号来源 | 大麦内与演出相关内容的多维互动；公开说明提到内容热度和任务贡献 | 是否简单累加、是否按用户质量分层、是否使用机器学习模型 |
| 时间维度 | 公开说明提到月榜，并称约每 10 分钟更新 | 10 分钟是实时计算周期、缓存刷新周期还是展示刷新周期 |
| 内容互动 | 发布、评论、点赞、分享等行为可影响内容热度 | 是否先给内容打分，再聚合到艺人/演出 |
| 反作弊 | 社区规则禁止刷屏、虚假互动、恶意刷榜、养号、诱导点击和水军行为 | 具体风控阈值、设备指纹字段、封禁模型和人工复核流程 |
| 搜索 | 帮助中心公开支持搜索明星、演出和体育赛事 | 搜索曝光、点击、停留、转化是否分开计分 |

## 3. 当前实现的真实计分模型

当前实现可以写成下面的公式。对某个艺人 `a`、榜单周期 `p`：

```text
score(a, p) = component_weight(component) × Σ event_weight(event) × quality(user) × diminishing_return
```

当前默认权重：

| 动作 | 默认分值 | 当前接入点 | 解释 |
|---|---:|---|---|
| detail | 1.0 | `GET /api/shows/{id}` | 用户打开演出详情后计入该演出艺人 |
| search | 0.3 | `GET /api/search/shows?keyword=` | 只有关键词和返回结果中的艺人名称相互匹配才计入，避免搜索演出标题给所有艺人加分 |
| purchase | 3.0 | 预约计划成功绑定创单请求后 | 只在创单请求被系统接受后计入，不在用户仅打开预约页时计入 |
| paid | 10.0 | 支付状态从待支付变为成功后 | 只有真实订单状态落库为已支付才计入 |

组件聚合权重为：内容 `0.40`、兴趣 `0.25`、购票意向 `0.15`、支付 `0.12`、任务 `0.08`。热榜在小时桶层再乘以 `2 ^ (-ageHours / hotHalfLifeHours)`，默认半衰期为 6 小时。

每个动作按“身份 + 艺人 + 自然日”去重：

```text
dedup = day + action + identity(userId or hashedIp) + sha256(normalizedArtist)
```

维护的 ZSET：

```text
ranking:artist:{component}:all
ranking:artist:{component}:daily:yyyyMMdd
ranking:artist:{component}:weekly:YYYY-Www
ranking:artist:{component}:monthly:yyyy-M
```

ZSET member 当前是规范化艺人名称的 SHA-256 截断 ID，例如 `artist:...`；展示名称写入 `ranking:{artist}:names` Hash，查询时再恢复名称。score 是经过质量系数和边际递减后的 Redis 浮点数；查询时再按组件权重和热榜时间衰减聚合。这样避免了名称直接作为 Redis member，但艺人别名归一化仍应由后续 `artist_profile/artist_alias` 主数据表负责。

## 4. 与大麦公开机制的差距

### 4.1 当前已经足够的部分

1. 使用 ZSET 保存“成员—分数”，天然支持高并发累加和 TopN 查询。
2. 搜索和详情两个用户入口已经分开计分，避免把所有行为混成一个不可解释的数字。
3. 购买意向和支付成功使用更高权重，符合“越接近真实交易，信号强度越高”的业务直觉。
4. 日、周、月榜分开保存，避免查询时扫描全量事件。
5. 通过用户 ID/IP 去重，能直接阻止最简单的重复刷新刷分。
6. Redis 非核心降级，不会因为排行榜故障导致无法购票或支付。

### 4.2 必须明确的不足

#### A. 不是大麦的“综合互动内容热度”

当前只有详情、搜索、创单、支付四类事件，没有内容发布、评论、点赞、分享和任务完成事件。因此当前榜单表达的是“购票/浏览热度”，不是“大麦公开描述的现场内容综合互动热度”。

如果产品目标是艺人购票热度，这个模型可以成立；如果产品目标是复刻“最热现场”，必须新增内容事件模型和任务事件模型。

#### B. 目前是周期内累加，没有时间衰减

本周第一天产生的 100 分和本周最后 10 分钟产生的 100 分权重相同。公开说明提到约 10 分钟更新和“热度”，这通常意味着需要新鲜度、事件速度或时间衰减；但大麦具体衰减函数没有公开。

当前热榜已经采用“时间桶 + 衰减聚合”，普通日/周/月榜仍保留周期累计口径，不要直接在一个永久累计 ZSET 上做复杂扣分：

```text
ranking:artist:event:yyyyMMddHH
score = Σ event_weight
read_score = Σ bucket_score × decay(now - bucket_time)
```

例如可先使用可配置的指数衰减：

```text
decay(ageHours) = 2 ^ (-ageHours / halfLifeHours)
```

`halfLifeHours` 必须通过历史数据回放校准，不能照抄大麦参数。

#### C. 艺人名称不是稳定主键

当前把 `show_info.artist` 直接作为 ZSET member，会遇到：

- “周杰伦”与“周杰伦（嘉宾）”被拆成两个成员；
- 乐队别名、英文名、全角半角、空格和大小写导致重复成员；
- 拼写错误或运营改名造成历史榜单断裂；
- 一场联合演出用逗号、`/`、`&` 存多个艺人时无法可靠拆分。

生产环境应增加稳定的 `artist_id`，另建艺人别名表：

```text
artist_profile(id, canonical_name, type, status)
artist_alias(id, artist_id, alias, normalized_alias, source)
show_artist(show_id, artist_id, billing_order)
```

ZSET member 应改成 `artist:{artistId}`，返回榜单时再关联规范名称。

#### D. 去重策略仍然偏粗

“同一身份、同一动作、同一艺人每天一次”能防刷，但会漏掉真实互动：一个用户一天内合理打开多个场次、完成多次有效互动，当前只算一次。

后续应按动作区分窗口：

| 动作 | 建议去重窗口 |
|---|---|
| 详情点击 | 同一艺人同一用户 30 分钟一次，或每天上限 N 次 |
| 搜索 | 同一关键词/艺人/用户 10 分钟一次 |
| 创单 | 同一订单请求幂等键一次 |
| 支付 | 订单号一次，必须由支付状态机触发 |
| 评论/点赞/分享 | 以内容 ID + 用户 ID + 动作做幂等 |

#### E. 当前四次 Redis 操作不是严格原子

现在是先写去重键，再分别 `ZINCRBY` 多个榜单并设置 TTL。若 Redis 在中间断开，可能出现“去重成功但分数没有完整增加”。

当前代码已经把“检查去重、写去重、五个 ZINCRBY、设置 TTL”放进 `lua/artist_ranking_record.lua`，保证同一事件的去重键、周期榜和小时桶要么全部生效，要么全部不生效。后续仍应把业务事件 ID 纳入幂等键，便于消息重放和补偿。

#### F. 反作弊还不能达到大麦级别

当前只使用登录用户 ID或哈希 IP。大麦公开规则还覆盖刷屏、虚假互动、养号、水军和诱导行为，因此至少应增加：

- 设备/安装实例维度；
- IP、账号、设备、手机号、支付账户的关联图；
- 单位时间行为速度（详情、搜索、创单的频率）；
- 新账号、异常地域、代理 IP、同设备多账号风险分；
- 事件状态：`accepted`、`suspected`、`rejected`，可疑事件不直接进入正式榜；
- 榜单异常波动告警和人工冻结/回滚能力。

## 5. 推荐的最终分层架构

不要让 Controller 直接决定分数，建议将链路分成四层：

```text
客户端行为
    ↓
事件采集层：detail/search/content/task/order/payment
    ↓
幂等与风控层：eventId、身份、频控、风险状态
    ↓
计分层：权重、时间衰减、艺人归一化、周期聚合
    ↓
查询层：TopN、分页、缓存、解释字段
```

查询结果不要只返回 `artist + score`，生产建议返回：

```json
{
  "rank": 1,
  "artistId": 1001,
  "artist": "周杰伦",
  "score": 1234.5,
  "trend": "UP",
  "scoreVersion": "v2",
  "updatedAt": "2026-08-08T14:40:00+08:00"
}
```

`scoreVersion` 很重要：调整权重后，前端和运营可以知道新旧分数不能直接横向比较。

## 6. 当前代码的上线判断

### 可以直接用于开发/测试环境

- ZSET key 设计和 TopN 查询；
- 详情、搜索、创单、支付事件接入；
- 日/周/月/全量榜；
- Redis 故障降级；
- 基础去重和 API 限流；
- 单元测试和 Maven 全量测试。

### 上生产前必须补

1. 艺人稳定 ID 和别名归一化，不能长期把自由文本作为 member。
2. 业务事件 ID 和消息幂等，避免同一订单/内容重放时依赖自然日去重。
3. 事件落库或消息队列，支持重放、补偿和审计。
4. 风控事件状态，不让所有 IP/账号事件直接进入正式榜。
5. 明确榜单口径：购票热度、艺人热度还是内容互动热度，不能混用。
6. 通过历史数据确定权重、衰减半衰期和榜单刷新策略。
7. 增加并发、Redis 故障、重复消息、支付回调重复到达测试。

### 不建议现在做的事

- 不要声称已经复刻大麦精确算法；
- 不要仅凭搜索次数定义“最热”；
- 不要把支付失败、订单超时、库存不足计入正向热度；
- 不要把用户输入的艺人字符串直接作为长期数据主键；
- 不要为了模仿“10 分钟更新”而让支付或下单依赖定时任务。

## 7. 验证方式

当前接口示例见 [`docs/api/artist-ranking.http`](../api/artist-ranking.http)。上线前至少验证：

1. 同一用户重复刷新详情不会无限刷分。
2. 未登录请求使用哈希 IP，不把明文 IP 写入 Redis key。
3. 搜索“周杰伦的演唱会”不会给所有返回演出艺人加分。
4. 创单失败、支付失败、支付回调重复不会增加支付成功分。
5. Redis 不可用时详情、搜索、创单、支付仍能完成。
6. 周/月跨边界时写入正确周期 key。
7. 并发事件不会出现去重成功但只有部分榜单增加的情况；当前已由 Lua 原子脚本覆盖。
